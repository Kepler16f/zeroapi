# WorkBuddy 深度融合方案（统一网关 / 统一调用）分拆

> 结论先行：不建议短期用 Dart 全量重写 `wb_proxy.py`（约 2 万行、含指纹/登录/
> 调度/任务等大量上游协议细节，重写风险与工期不可控）。推荐 **「D 方案」**：
> 保留 Python 号池作为受管引擎，由 ZeroApi 逐步收编生命周期、控制面与数据面，
> 最终形态对用户与客户端只有一个网关 `127.0.0.1:8123`、一套账号/用量/任务视图。

## 一、现状盘点

| 能力 | 现在由谁负责 | 关键位置 |
|---|---|---|
| 统一网关（OpenAI/Anthropic 兼容、密钥、限流） | ZeroApi (Dart) | `lib/gateway/proxy.dart` |
| 模型注册与调用名（`zen/…`、`WorkBuddy/…`） | ZeroApi | `ModelRegistry.rebuild` |
| 供应商目录探测 / 健康 | ZeroApi | `lib/gateway/upstream.dart` |
| 代理池（http/socks5 直连、加密协议 mihomo、轮换/冷却） | ZeroApi | `proxypool.dart` / `proxycore.dart` |
| WorkBuddy 账号池、登录、上游鉴权、指纹 | Python hub | `vendor/workbuddy2api-hub/wb_proxy.py` |
| 双区出口（codebuddy.cn / workbuddy.ai） | Python hub | `detect_model_realm`、`open_upstream` |
| 用量/成本/积分记录 | Python hub（usage.jsonl） | `wb_usage.py` 等 |
| 签到 / 每日活跃 / 任务 / 调度 | Python hub | `wb_activity.py`、`/accounts/checkin` |
| 号池 UI（账号、签到、任务、调度） | ZeroApi 原生页（本轮补齐签到中心） | `hub_dashboard.dart`、`checkin_page.dart` |

耦合方式：ZeroApi 把 hub 当成**一个 OpenAI 兼容上游**（`http://127.0.0.1:8788/v1`），
管理面走 `/panel/login` 换 token 后的管理 API。本轮已补上双区路由的关键一环：
ZeroApi 探测双目录时记录每个模型的出口区，转发时按需带 `X-Realm`（独占模型必带、
共有模型按用户「优先出口」开关），彻底解决「国内/国际同开但国际模型 400」。

## 二、目标状态（用户视角）

1. 只有一个入口：`http://127.0.0.1:8123/v1`，模型清单里 `zen/…` 与
   `WorkBuddy/…` 按来源分组，`WorkBuddy/` 下国内/国际模型都能直接调用。
2. 只有一份账号视图：ZeroApi「账号」页 = 号池账号（登录、禁用、额度、签到、
   熔断状态），没有第二个网页面板需要记住地址/密码。
3. 只有一份用量/成本：用量页同时覆盖 zen 与号池，口径一致（按模型、按天）。
4. 只有一套任务：签到中心、每日活跃、调度状态都在主应用内操作与查看。
5. 用户无感：不需要知道有 Python 进程、端口、面板密码；卸载即全清。

## 三、方案候选对比

| 方案 | 内容 | 工期/风险 | 结论 |
|---|---|---|---|
| A. 保持现状 + 修修补补 | UI 继续用 WebView/跳浏览器 | 低，但双份数据源/双份 UI 长期不可维护 | 否 |
| B. 协议核心 Dart 化、账号池留 Python | 重写上游请求/指纹/流式协议 | 极高（上游反爬细节多、回归难） | 暂缓 |
| C. 全量 Dart 重写 | 单二进制 | 极高，等于重做 hub | 否（长期可评估） |
| **D. 受管引擎 + 控制面/数据面收编（推荐）** | hub 作为应用内受管进程，ZeroApi 提供全部 UI 与统一数据面 | 中，可分 5 期落地 | **是** |

## 四、D 方案分拆（按依赖顺序）

### 阶段 0（已完成，本轮）
- 双区路由：目录探测记录 realm，转发带 `X-Realm`；用户可设「共有模型优先出口」。
- 原生签到中心（国内签到 / 国际每日活跃 / 签到记录），不再依赖网页面板。
- 供应商卡片单家刷新；出口代理「手写地址 / 内置代理池」二选一。
- 代理组订阅刷新：绑定订阅链接后手动/自动（6h）刷新、整组替换；
  大面积冷却时优先刷新；支持钉住指定节点。

**验收**：`/v1/models` 同时列出两区模型；国际独占模型调用不再出现
「Key 绑定国内版出口」400；签到中心可完成一次真实签到。

### 阶段 1：生命周期与配置单一来源（≈1 周）
- hub 端口从固定 8788 改为**启动时探测空闲端口**，写回 `baseUrl`，避免冲突。
- 进程守护：异常退出自动重启（指数退避）、启动失败给出可操作错误；
  应用退出时确保子进程树清理（含 Python 孙进程）。
- hub 的 `--accounts-dir/--usage-dir/--catalog-dir` 等参数全部由 ZeroApi
  config 生成，用户可见的配置项收敛到设置页，不再手改 args。
- 健康面板：进程/端口/账号池就绪度、最近错误，一键重启号池引擎。

**验收**：杀掉 pythonw 后 10 秒内自动恢复；8788 被占用时应用正常启动并换端口；
退出应用后无残留 python 进程。

### 阶段 2：控制面原生化（≈2 周）
- 账号管理：启用/禁用/权重/禁用模型、手动导入/导出、登录（扫码/桌面授权）
  全部进入账号页（登录流程优先复用 hub 的 `/accounts/login/*` API）。
- 调度与熔断：展示并调整调度开关（轮询/剩余优先/每日限额）、冷却与风控状态。
- 任务：签到中心已具备；补每日活跃的「未活跃账号列表」与一键补打、任务奖励查看。
- 面板密码与 WebView 入口降级为「高级排障」隐藏菜单。

**验收**：账号页完成增删改查+登录+签到，全程不打开浏览器。

### 阶段 3：数据面统一（≈1–2 周）
- 事件流：hub 每次请求完成写 usage 事件（已有 usage.jsonl），ZeroApi 增量
  读取（按字节偏移 tail）并入统一用量库，替代当前「窗口聚合 + 合并展示」。
- 定价单一来源：`pricing.json` 只保留一份（ZeroApi 资源），hub 通过 API 读取；
  成本计算在一处完成，避免两套口径。
- 用量页支持按「来源 × 模型 × 天」下钻，与 zen 完全同构。

**验收**：同一天同一请求在应用内只出现一次；成本与上游账单误差 < 1%。

### 阶段 4（可选，长期）：协议核心瘦身
- 仅当「必须去掉 Python 运行时」成为硬需求时启动：先做 Dart 只读影子客户端
  （复现登录后请求、与 Python 结果比对），稳定后再切流；账号池与调度仍留在
  Python 侧，逐步迁移。
- 在此之前保持 D 方案：Python 是受管引擎，不是用户可见的产品面。

## 五、本轮已落地的接口约定（后续阶段依赖）

- ZeroApi → hub 注入 `X-Realm: cn|intl`（仅独占模型与用户偏好共有模型）。
- ZeroApi 记录每个上游模型的 `modelRealms`（仅单区独占），`/v1/models` 的
  `zeroapi.realm` 暴露给客户端。
- 管理面统一 `hubGet/hubPost`（面板 token 自动登录、401 重登、超时与错误上抛）。
- 签到中心消费：`GET /accounts`、`GET /activity/history`、
  `POST /accounts/checkin`、`POST /accounts/daily-chat`。

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| hub 版本升级覆盖本地补丁 | 补丁集中在 `wb_proxy.py` 极少数位置并加 `PATCHED-BY-OPS` 标记；升级脚本检查标记 |
| 双区账号额度不均导致国际模型失败 | 错误原样透出（11140/11158 等上游码），引导用户添加对应区账号；不做静默转投 |
| 自动刷新订阅过于频繁 | 6h 定时 + 30 分钟失败限流 + 自动刷新开关（组级） |
| 用例/回归依赖真实号池 | 数据层用 fake hub（widget 测试），真实 I/O 用普通 test；发布前跑一次真机联调 |
