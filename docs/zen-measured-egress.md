# Zen 出口：全量测速后选路（2026-11-01）

## 问题与方案

旧版在请求前仅从现有候选里依次探三个，未等待完整测速；普通巡检失败时又保留旧延迟。
因此三个可能恰好全是失效节点，而可用节点排在后面。候选列表变化时继续推进位置游标还会跳过节点。

现在对 **Zen 当前绑定分组的全部节点** 做目标站检测，完成后再选路。保持分组边界，
不借用 Webshare，不修改系统代理。这里的测速是访问目标站的响应耗时，不是下载带宽测试。

- 每批最多并发 8 个，检测目标为当前登记的 `https://opencode.ai/`。
- 单个检测从建连、接收头到读完响应体共用 8 秒上限；超时/异常/HTTP 4xx、5xx 剔除。
- 本轮全部结束后，成功项按目标站耗时升序排列；旧延迟不作为未测/失败节点的兜底。
- 同用途的并发调用等待同一轮检测；结果仅在内存保留 60 秒。节点、参数、端口、绑定或目标变化即重新检测。
- 保留手动固定节点语义：固定节点通过检测时优先使用；失败后才回退到组内检测成功项。
- 单次请求首发与重试总计最多三个不同节点；记录已尝试的节点身份，候选列表变化也不重复。
- 已收到模型输出或思考后不再自动重发。全部失败返回具体错误，不降级到未绑定分组或直连。
- 请求测速、切换期间延后后台内核/CLI 更新；切换出口后等待 CLI 就绪再重发。
- 普通巡检失败清除旧延迟，探测结束必关客户端，响应体挂起也受超时约束。

首页可达不代表上游允许模型生成；真实调用的额度拒绝仍按上游错误返回。
